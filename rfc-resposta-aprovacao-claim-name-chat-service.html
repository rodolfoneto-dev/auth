1. Mensagem da Liderança Técnica

Prezado Bob e equipe do chat-service,

Agradecemos pela excelente condução técnica e clareza estrutural apresentada na RFC-CHAT-001. A análise comparativa de alternativas demonstra alto rigor arquitetural, e concordamos integralmente que a inclusão dos dados de identificação diretamente no token JWT é a abordagem com menor latência, maior segurança contra spoofing e zero sobrecarga de tráfego síncrono no ecossistema.

Parecer Favorável: A solicitação foi aceita e implementada no auth-service. Tanto o campo name quanto o campo email foram incorporados de forma definitiva e padronizada a todos os tokens JWT emitidos pela plataforma.

3. Ponto de Consideração para o chat-service: Governança & Zero Trust

Recomendação de Governança de Produto e Segurança: Para manter a integridade das salas de aula, preservar o ambiente pedagógico e evitar contas de spam/trolls descartáveis, solicitamos a consideração da equipe do chat-service para adotar a seguinte regra de acesso ao chat:

O usuário só deve ter permissão para conectar e enviar mensagens no chat se cumprir cumulativamente os dois requisitos:

RequisitoClaim no JWTObjetivo / Benefício
1. Usuário Ativo status === "active" Bloqueia imediatamente usuários suspensos por moderação, expulsos ou com pendência cadastral.
2. E-mail Confirmado emailVerified === true Anti-Spam & Proteção de Identidade: Impede que invasores usem provedores temporários (ex: tempmail) para acessar chats públicos e importunar outros estudantes ou docentes.

Por que isso é extremamente vantajoso para o Chat Service?

  • Zero Custo de Rede (100% Stateless): O chat-service não precisa fazer nenhuma requisição HTTP ao banco de dados do auth para checar essa regra. Ambas as flags (status e emailVerified) já estão assinadas criptograficamente dentro do token JWT entregue no handshake.
  • Sem Fricção em Staging e Dev: Todos os usuários de teste (aluno@upexperience.com.br, professor@..., admin@...) e as ferramentas de geração de token (DevPortal e npm run token:gen) já emitem status: "active" e emailVerified: true por padrão.
  • Defesa em Profundidade: Garante que um usuário não contorne validações visuais do frontend conectando via WebSocket client avulso.

Sugestão de Implementação no Handshake Socket.io

// src/middleware/auth.middleware.js — chat-service
io.use((socket, next) => {
  const token = socket.handshake.auth?.token || socket.handshake.headers?.authorization;
  if (!token) {
    return next(new Error('AUTHENTICATION_ERROR: Token JWT ausente'));
  }

  const rawToken = token.startsWith('Bearer ') ? token.slice(7) : token;

  try {
    const decoded = jwt.verify(rawToken, JWT_SECRET);

    // 1. Validação de Conta Ativa
    if (decoded.status && decoded.status !== 'active') {
      return next(new Error('FORBIDDEN: Conta de usuário inativa ou suspensa'));
    }

    // 2. Validação de E-mail Verificado (Sugestão Solicitada)
    if (!decoded.emailVerified) {
      return next(new Error('FORBIDDEN: Confirme seu e-mail institucional antes de acessar o chat'));
    }

    socket.user = {
      id:    decoded.sub || decoded.id,
      name:  decoded.name,   // ← Nome real do usuário disponível
      email: decoded.email,  // ← E-mail verificado disponível
      role:  decoded.role || 'aluno',
    };

    next();
  } catch (err) {
    return next(new Error(`AUTHENTICATION_ERROR: ${err.message}`));
  }
});
